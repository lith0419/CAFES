# CAFES Knowledge Wiki

This directory is the local knowledge base for the CAFES project.
It is designed for `llm-wiki-compiler` (`llmwiki`), which compiles raw
Markdown sources into an interlinked wiki.

## Purpose

The project now contains many rules spread across code, prompts, UI behavior,
and debugging history. This wiki keeps those rules durable, searchable, and
auditable.

Use this directory for:

- Agent architecture notes
- Workflow and state rules
- Model Hamiltonian input and planning rules
- Planner-agent behavior rules
- PySCF method and solver support
- UI navigation and approval boundaries
- Error-book entries from real failures
- Adaptive workflow states, approval gates, and recovery rules

## Layout

```text
agent_knowledge/
  conversation_rules/
                Conversation-derived rule inbox for later maintainer review
  sources/      Raw source notes maintained by humans and agents
  wiki/         Generated by llmwiki compile
  .llmwiki/     Compiler state, candidates, lint/eval data
```

Only `sources/`, `conversation_rules/`, and the maintained
`curated_structure.json` routing/guidance file should be edited by hand. The
`wiki/` and `.llmwiki/` directories are generated by the compiler.

`conversation_rules/` is an inbox for rules discovered during agent/user
work sessions. These notes are intentionally kept outside `sources/` so they
do not enter the main wiki until a maintainer reviews, merges, and recompiles
them.

## Build The Wiki

`llm-wiki-compiler` is a Node.js CLI. It requires Node.js >= 24.

```bash
cd agent_knowledge
npm install
```

The local helper script first tries to reuse the OpenAI-compatible CAFES
LLM configuration. From the repository root, load the private local file before
entering this directory:

```bash
python configure.py init-llm
# Edit ./llm.env, then:
source ./llm.env
cd agent_knowledge
```

For `llmwiki compile`, the selected model must support tool calling. If the
agent model is a reasoning/thinking model that rejects `tool_choice`, keep the
agent configuration unchanged and override only the wiki model:

```bash
export LLMWIKI_MODEL="a-tool-calling-model"
```

You can also configure `llmwiki` directly. Example with Ollama:

```bash
export LLMWIKI_PROVIDER=ollama
export LLMWIKI_MODEL=llama3.1
export LLMWIKI_EMBEDDING_MODEL=nomic-embed-text
export OLLAMA_HOST=http://localhost:11434/v1
```

Use LLM compilation only to discover or refresh candidate concepts. It should
not write directly to the runtime wiki unless a maintainer intentionally wants
to inspect the raw compiler output.

```bash
npm run wiki:compile:review
npm run wiki:review:list
npm run wiki:review:bundle
```

The review bundle writes:

- `.llmwiki/review-export/review-candidates.md`
- `.llmwiki/review-export/review-candidates.html`

The runtime wiki is the curated action guide, not the raw direct-compile
output. After reviewing sources and candidate material, generate the curated
wiki layout:

```bash
npm run wiki:curate
npm run wiki:lint
```

The curated layout is controlled by `curated_structure.json`. When adding a
new durable rule page, add its route and guidance there as well so the planner
can retrieve it. It writes local review pages to `wiki/concepts/`, produces
optional review exports under `.llmwiki/review-export/`, and updates the single
tracked runtime export:

- `computational_study_agent/knowledge/curated_wiki.json`

Curated pages intentionally collapse many generated candidates into a smaller
set of LLM-facing action-guide pages. They preserve provenance through frontmatter
`sources`, but inline claim citations are stripped because merged candidate
pages can contain malformed or obsolete source-line references.
The planner retriever consumes the packaged runtime export. Direct compile
output never becomes a second runtime knowledge source.

For a matching page title/source route, maintained `sources/` notes take
precedence over historical compiler candidates and published exports.
`pageGuidance` is an explicit editorial replacement of that page body, not an
automatic summary of its source. When a guided rule changes, update both the
source and its `pageGuidance` entry before curating. Unguided pages use the
maintained source body. Curation itself is deterministic and makes no LLM call.

Runtime retrieval uses English scientific query terms, local keyword ranking,
and bounded relevant passages from this export. It does not send the full Wiki
or Registry to the LLM. Validate the actual retrieved passages after content
changes, not only the generated page count. The packaged export is read on each
retrieval; updating it does not require restarting the service. Changes to
Python retrieval/planner code do require reloading that code.

Avoid using direct compilation as the normal publishing flow:

```bash
npm run wiki:compile
```

Direct compilation writes raw generated pages into `wiki/`. Those pages can be
useful for exploration, but they may be too granular or contain broken generated
links. If direct compilation is used, run `npm run wiki:curate` afterward before
trusting runtime retrieval.

`llmwiki` 0.9.0 scans Markdown files directly under `sources/`, so source
filenames include topic prefixes such as `model-hamiltonian-*` and
`planner-agent-*`.

## Rule Extraction

After a successful compile, extract actionable rule candidates:

```bash
llmwiki rules extract
llmwiki rules list
llmwiki rules approve <candidate-id>
llmwiki rules export
```

Approved rules can later be converted into a Codex skill. The wiki should
remain the detailed source of truth; the skill should contain only compact,
high-priority execution rules.

## Maintenance Guidelines

- Capture conversation-derived rules in `conversation_rules/` first.
- Periodically merge stable inbox notes into `sources/`, then curate.
- Add a new source file for each important design rule or failure case.
- Prefer concrete examples over broad prose.
- Include rationale and known failure modes.
- Keep implementation facts tied to the current codebase.
- When behavior changes, update the source first, then regenerate the curated wiki.
- Use `llmwiki lint` before trusting the runtime wiki.
